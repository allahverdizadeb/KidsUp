## Commands

- Setup: `python -m venv .venv`, activate, `pip install --require-hashes -r requirements-dev.txt` (hash-pinned lock)
- Database: local Postgres on `localhost:5432` (user/password `postgres`, db `kidsup`); `alembic upgrade head`
- Run the public API: `uvicorn app.main:app --reload` (http://localhost:8000, docs at `/docs` in development only)
- Run the admin API (its own application, port and database account): `KIDSUP_PANEL_SECRET_KEY=<a Fernet key> KIDSUP_PANEL_CONTENT_DIR=<a folder> uvicorn app.panel.main:create_panel_app --factory --port 8001`
  (`python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"` makes a key). One worker. It writes `courses.json`, `site.json` and
  `media/` into that folder; the landing page reads them from `/content/` and `/media/` in Docker (Vite does not serve them: use Docker to see published content).
- **Definition of done:** `ruff check .`, `ruff format --check .`, `mypy`, `bandit -q -r app -c pyproject.toml`,
  `pip-audit --require-hashes -r requirements.txt`, `python -m pytest` (tests + **coverage gate 80%**, currently 100%)
- Tests need a real **local** Postgres with a superuser (the schema uses arrays, triggers and row locks; the bootstrap tests create and drop the scratch database `kidsup_bootstrap_test` and the `kidsup_*_test` roles) and use `kidsup_test`; override with `KIDSUP_TEST_DATABASE_URL`, which must name a local database ending in `_test` (the suite refuses anything else). Never test against SQLite. `tests/test_compose.py`, `tests/test_container.py` and `tests/test_admin_nginx.py` also read `../docker-compose.yml`, `../db/Dockerfile` and `../admin/` (they move to the admin project once it has its own tooling).
- Dependencies: edit `requirements.in` / `requirements-dev.in`, then regenerate the locks with
  `uv pip compile … --universal --generate-hashes` (exact commands in `docs/coding-standards.md` §8). Never hand-edit a lock.
- New migration after a model change: `alembic revision -m "what changed"`, then edit by hand and review (`docs/api-and-database-standards.md` §4). Migrations run as the schema owner; never touch applications' rows destructively.
- Docker: `docker compose up --build` from the repo root. A one-off `bootstrap` job (`python -m app.bootstrap`) creates the five database accounts (superuser, owner, API, retention, panel), runs `alembic upgrade head` as the schema owner and grants the other three exactly their rights (`app/grants.py`), then `back` and `panel` start. Neither migrates; each refuses to start with a wider (the panel: also a narrower) account than its own. See `../docs/docker.md`.
- Operator commands for applications, inside the **retention** container (its account may delete; the API's may not): `docker compose exec retention python -m app.cli purge-expired [--dry-run] [--force] | erase-application <id> | erase-by-phone` (the purge stops by itself at more than 50 applications due, see `../docs/docker.md`). They log counts, application ids and dates, never names or phone numbers. There is no command that approves an application: only the panel does, with the capacity check.
- Operator commands for staff accounts, inside the **panel** container: `docker compose exec panel python -m app.panel.cli create-admin --email … --name … --role viewer|coordinator|admin` and `list-admins | reset-password | reset-second-factor | set-role | deactivate | activate | unlock`. Passwords and the one-time-code check are typed at prompts, never given as arguments. There is no sign-up and no screen for accounts.

## Layout (request flows router → service → database, each layer hands the rest on)

- `app/main.py`: `create_app(config)`: the public API, wiring only (middleware, routers, docs on/off). `app/panel/main.py`: `create_panel_app(config)`: the admin API, a separate application (own container, own database account, own limits).
- `app/config.py`: `Settings` from `KIDSUP_*` env vars (see `.env.example`); accepts `postgres://` URLs; refuses wildcard hosts/origins in production.
- `app/middleware.py`: security headers (also on 500 answers), body-size limit. `app/rate_limit.py`: per-client limiter (`enforce_rate_limit` dependency).
- `app/db.py`: engine (parameters hidden from error text), session, `Base`. `app/models.py`: tables and enums. `app/grants.py`: what each account may do, table by table and column by column. `app/privileges.py`: the start-up checks (the API's account may insert into the application tables and do nothing else; the panel's holds exactly its grants). `app/database_errors.py`: the SQLSTATE codes of the course rules.
- `app/bootstrap.py`: the one-off job that sets up the five database accounts, migrates and grants (`SEC-B-07`); it talks to the database itself, the one exception to "only services touch the database" (it creates the accounts the services run as). `app/cli.py` + `app/services/retention.py`: retention and erasure (`SEC-B-09`). `app/logging_config.py`: the log format of the commands.
- `app/routers/`, `app/schemas/`, `app/services/`: the public API. HTTP only / models and validation / logic.
- `app/panel/`: the admin API, same layering: `routers/` (auth, applications, courses, dashboard, content, audit), `schemas/`, `services/` (sessions, passwords with Argon2id, TOTP, secret box, audit, text search, CSV export, courses, dashboard, content, pictures, the public files `snapshots.py` / `public_site.py`), `security.py` + `permissions.py` (default-deny `require(permission)`, CSRF, origin check), `content_registry.json` + `content_registry.py` + `content_values.py` (the places of the landing page staff may edit and the rules for what may be written), `cli.py` (staff accounts).
- `alembic/versions/`: migrations. `tests/`: pytest, mirrors topics of `app/` (`tests/panel/` for the admin API).

## Public API (the contract; `front/` reads it from here)

- `GET /health`: unauthenticated, no DB access (deploy checks), reveals nothing.
- `POST /api/applications` → `201 {"id": "<uuid>"}`, `422` validation details, `409 {"detail": "Registration is closed."}` (the course is closed, full or unknown, or no single course is open and none was named), `413`/`411` body too large/missing length, `429` rate limit (`Retry-After: 60`). Body:
  - `parent_name` (required, trimmed, ≤120; control characters and text-direction overrides refused, runs of whitespace become one space), `phone` (≤32, 9–12 plain ASCII digits, only digits/space/+/()/-; any whitespace such as a no-break space becomes one space)
  - `children`: 1–2 of `{ name (≤120, same rules as the parent's), birth_date }`; birth date must be within 2010-01-01..2020-12-31
  - `languages`: 1 to 3 of `Azərbaycan`, `Rus`, `İngilis` (at most 3 are accepted before duplicates are dropped)
  - `course_id` (optional UUID): the course applied for, one of `courses.json`. Left out, the database picks **the one open course**; with none or several open it answers 409. The choice is made by the database itself (trigger `applications_pick_course`), so it holds whatever writes the row.
  - `consent`: must be the JSON value `true` (not `1`, not `"true"`, not missing): the parent's explicit yes (`SEC-F-16`)
  - `privacy_notice_version`: the version of the notice the parent saw: `YYYY-MM-DD` with an optional suffix `-[a-z0-9]{1,16}` (`2026-10-19`, `2026-11-02-v2`), ≤32, and **one of `PUBLISHED_NOTICE_VERSIONS`** in `app/schemas/application.py` (a consent is stored only against wording that was really shown and approved by counsel; the draft `2026-10-19-draft` is retired and refused). A new version is added there in the same change that edits `front/src/content/privacyNotice.ts`, and the API is deployed first.
  The 8–13 age rule is deliberately **not** enforced: the design only warns the parent (age is measured on the start date of the course). Staff see `age_at_course_start` and `within_age_range`.
- Public by design (listed here per `SEC-B-04`): `/health` (inside the network only: nginx passes on nothing but `POST /api/applications`) and `POST /api/applications`. Everything else is authenticated, default deny. A trailing slash (`/api/applications/`) is a plain 404.
- Limits: `KIDSUP_MAX_BODY_BYTES` (16 KiB), `KIDSUP_RATE_LIMIT_PER_MINUTE` (10 per client, per instance).
- Stored in `applications` (+ `application_children`): `status` starts as `new` and is one of `new`, `contacted`, `approved`, `declined` (database CHECK); `course_id` (NOT NULL, foreign key to `courses`); `consent_given_at` (the database's clock) and `privacy_notice_version` (both empty only for rows from before 2026-10-18). The API's account can only INSERT: it cannot read any of it back, and it may insert only the columns the form fills in (`APP_GRANTS` in `app/grants.py`): never `status`, `status_changed_at` or `created_at`, so a new application always starts as `new` at the database's clock. A child has the position 0 or 1, unique per application (migration 0011), so an application brings one or two children whoever writes the rows.
- **A submission is not a registration.** A form creates an application with status `new`; it takes no place. A **place is taken by an approved child** (`approved` application → its children), counted by `course_seats_taken(course)` in the database. Approving is refused (`KU002`, under a row lock on the course) when the children no longer fit, so a course never holds more than its capacity however many staff approve at once. A course that is full takes no further applications (`KU001`).
- Applications that were not approved (`new`, `contacted`, `declined`) are deleted after `KIDSUP_RETENTION_DAYS` (default and maximum 365: the notice promises 12 months) by the daily `retention` job; an `approved` one is kept until it is erased on request. A failing run ends the job's container, so it shows up as a restarting container.
- Production (`KIDSUP_ENVIRONMENT=production`): no `/docs`, `/redoc`, `/openapi.json`; HSTS on; explicit `KIDSUP_ALLOWED_HOSTS` / `KIDSUP_CORS_ORIGINS` (the developer's defaults are refused, not just `*`).
- A refused request (`422`) answers `{"detail": [{"loc": [...], "type": "..."}]}`: where the fault is and what kind, never the value that was sent (`app/middleware.py: validation_error_handler`, both APIs). The `Cache-Control` of a picture is one day; the page's pictures can be removed again by an admin.

## Admin API (`/api/admin/...`, served by its own container; the admin panel and the landing page's content consume it)

Everything but signing in needs a session, and each route names the permission it needs (`app/panel/permissions.py`: `viewer` reads; `coordinator` also changes statuses and writes notes; `admin` also exports, erases, edits courses and the landing page and reads the audit log; taking an approval back, i.e. leaving `approved`, needs the right to erase too: 403 `approval_locked` for a coordinator, because the retention job deletes what is not approved). A request without the permission is 403, without a session 401, and a state-changing request without the CSRF token or from another origin is refused. Search terms and filters travel in `POST` bodies, never in the address.

- Session: `POST /api/admin/sessions` `{email, password, code}` → 201 `{admin{email, display_name, role, permissions[]}, csrf_token, idle_timeout_seconds}` + the cookie `__Secure-kidsup_admin` (HttpOnly, Secure, SameSite=Strict, path `/api/admin`); every failure is the same 401. `GET`/`DELETE /api/admin/sessions/current` (who am I / sign out, revoked on the server). `PUT /api/admin/account/password`. Send the token in `X-CSRF-Token` and the page's origin in `Origin` with every request that changes something; a request that only polls sends `X-Background: poll` so it does not extend the session. A session ends after 15 idle minutes (`KIDSUP_PANEL_SESSION_IDLE_MINUTES`, never more) and after `KIDSUP_PANEL_SESSION_MAX_HOURS` (8, never more) however busy. A wrong current password in `PUT /account/password` counts toward the same lock as a wrong sign-in (the fifth ends every session of the account), shares the sign-in's per-address limit and is audited as `password_change_failed`.
- Applications: `POST /api/admin/applications/search` `{search?, statuses[], course_id?, language?, created_from?, created_to?, sort, limit, offset}` → `{items, total, limit, offset}` (a name or part of a phone number, accents and case ignored); `GET .../pulse` (counts and the time of the latest, no personal data: what a page polls); `GET .../{id}` (the detail with notes, consent and notice version; audited); `PATCH .../{id}` `{status}` (409 `not_enough_seats` with `needed` and `free_seats` when approving would overfill the course); `DELETE .../{id}?confirm=true` (an erasure at a parent's request; `confirm` is required); `POST .../{id}/notes` `{body}` (up to 200 notes per application: 409 `too_many_notes`; no control characters except line breaks and tabs); `DELETE .../{id}/notes/{note_id}`; `POST .../export` (same filters → CSV, `Content-Disposition: attachment`; cells that start with `=`, `+`, `-`, `@` are neutralised; 5 a minute; audited).
- Courses: `GET`/`POST /api/admin/courses`, `GET`/`PATCH`/`DELETE .../{id}`. A course has `title`, `start_date`, `schedule`, `location`, `age_min`, `age_max`, `price_minor` and `second_child_price_minor` (whole qəpik: 1 AZN = 100), `currency` (`AZN` only), `capacity` (1–500), `registration_open`, and read-only `seats` (`capacity`, `approved_children`, `free_seats`, applications by status). 409 `capacity_below_approved` when capacity would go below the approved children; 409 `course_has_applications` on deleting a course someone applied to (close it instead).
- Dashboard: `GET /api/admin/dashboard?days=30` → totals (applications, by status, approved children, free seats), the courses with their seats, the latest applications, and applications per day. All of it is computed from the stored rows on each call.
- Landing page content: `GET /api/admin/content` (every editable place with its default, draft and published value), `PUT` (`{values: {key: value|null}}`: saves a **draft**, one bad value saves nothing, `null` puts the default back), `POST .../content/publications` (makes the draft live: writes `site.json` atomically and keeps every publication as history), `GET`/`POST /api/admin/media` (the body of the `POST` is the picture itself: PNG, JPEG or WebP up to 5 MiB and 16 megapixels, decoded one at a time, re-encoded as WebP without metadata and named by a new random id; the same picture again is the same picture and puts its file back if it is gone), `DELETE /api/admin/media/{id}` (removes the row and the file; 409 `media_in_use` while the draft or the live page shows it, so a photo whose parent withdrew consent can be taken down; audited). Publishing fails with `missing_image_file` if a chosen picture's file is not there. The phone number needs a country code (`+994…`), the WhatsApp number is 10–15 digits that do not start with 0, and the three links accept only the hosts their place names (`hosts` in the registry). The list of places is `app/panel/content_registry.json`; **`front/src/content/registry.json` must be an identical copy** (a front test compares them byte for byte). Texts may contain the names `{price}`, `{price_second}`, `{price_double}`, `{price_family}`, `{price_saving}`, `{saving_percent}`, `{capacity}`, `{age_min}`, `{age_max}`, `{start_date}`, `{schedule}`, `{location}`, which the page fills from the course it shows; paragraphs may mark **bold** with `**`.
- `GET /api/admin/audit?action=&limit=&offset=`: the audit log, newest first (who, what, which record, from which network; never a name, a phone number, a note or a search term). A listing, the dashboard and an export record the **ids** of the applications they showed, so a misused account or a leaked file can be traced to its families. The database refuses to change or delete an entry (the runtime accounts; a superuser or the owner can switch the triggers off: `docs/security-standards.md` §5 entry 15).
- What the public site reads is **not** an API: the panel writes `courses.json` (the open courses with `seats_left` and `accepting_applications`) and `site.json` (the published places) into the `content` volume, which nginx serves read-only at `/content/`; pictures are `/media/<uuid>.webp`. The files are rewritten after every change, at start-up and every minute.

## Rules (the short list; the documents above are authoritative)

- Security first (`docs/security-standards.md`). Every control touched has a test that fails if the control is removed.
- Layering: `routers → services → models`; routers hold no queries; services import no `fastapi`.
- No string-built SQL, no secrets or personal data in code/logs/errors/fixtures, never log phone numbers or children's names, never put a search term in a URL.
- Public endpoints are `/api/…` and the admin ones `/api/admin/…`; never `*` for CORS/hosts in production. Schema changes only through Alembic.
